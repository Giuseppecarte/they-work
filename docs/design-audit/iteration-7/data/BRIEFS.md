# Implementation-ready candidates

These are proposed changes, not changes made by the discovery audit. Ranking is local to the data findings; the product roadmap may rank them against onboarding and control safety.

## D1 — Make stream gaps explicit and retry unresolved observations

**Priority:** high. **Problem:** the supervisor's bounded event ring can advance past the consumer, while the UI only reports general source limitations. An event with an unknown actor is skipped and can be stranded after the cursor advances. The reproduced inputs and expected semantic facts are in [results.json](evidence/results.json).

**Scope correction from the [dual-feed follow-up](DUAL-FEED.md):** the independent collector recovers native relationship metadata and recent results. The reproduced integrated delivery miss is conditional on a cold collector and results older than its per-thread tail. Preserve recovered facts and do not turn a raw stream gap into a blanket claim that all family/result evidence is unavailable. Include all three integrated cases in implementation acceptance.

**Chosen behavior:** preserve the current live observer model. The first implementation must detect and display known loss, retain valid current roster/approval state, and retry still-available observations once their participant becomes known. It must not claim complete recovery, silently widen access to source stores, introduce an unlimited journal, or replay a user instruction. Read-only transcript backfill is a separate capability-dependent follow-up, not a prerequisite for truthful coverage.

**Interfaces and ownership:**

1. Control exposes a versioned `EventWindow` with stream identity, first retained sequence and last assigned sequence. Its identity must describe the stored sequence lineage, not a display title. New stream identity is required if sequence numbering resets; process restart alone must not accidentally join unrelated streams. Default/deserialized legacy state means continuity unknown, never complete.
2. Replace the host's bare sequence with a `BridgeCursor { stream_id, applied_sequence, deferred }`. A new `reconcile_snapshot` returns `BridgeBatch { events, next_cursor, continuity }`; preserve `snapshot_events` as a compatibility wrapper until its callers migrate. `continuity` distinguishes contiguous data, exact sequence gap, new/unknown stream, and unresolved participant loss.
3. `deferred` is a bounded map keyed by source identity plus native actor and sequence. Retry after each roster update. Do not fabricate a worker, role or parent to process the event. Start with at most the existing 256-event window; use an explicit loss diagnostic when the bound or stream change forces eviction. Account for any empty snapshot without resetting a valid cursor blindly.
4. Core coverage gains optional structured continuity metadata, separate from source freshness, recovered semantic records and the existing `incomplete` flag. Its explicit unit is `ProviderStreamEvent`: an incoming provider notification or server request sequenced by the host, including an approval request with a JSON-RPC ID. It is not a result, task, database row or semantic change; many stream events can be deltas for one record. A live provider can be fresh while its provider event stream has a gap. The renderer receives facts, not protocol parsing. Example: `44 live provider events were skipped. Local history may recover work records; current approvals remain available.` If the collector supplied records, say which records are available without claiming that all semantic evidence was recovered. Short layouts retain a concise warning and expose full detail in the inspector.
5. Advance the applied cursor only with the returned batch's state after the caller has applied it. Continue native-ID deduplication. Keep unresolved items separately from the high-water mark so one missing actor cannot stall every other conversation.

**Migration:** additive serde defaults for stored control state and coverage. Existing notebook reading markers retain their meaning and keys. Old snapshots are `continuity unknown`; do not infer `0 missing` from absent metadata. Keep connection ownership and request IDs unchanged. This change must not alter the operation receipt/idempotency ledger.

**Failure handling:** gap calculation tolerates an empty window, duplicate snapshots, out-of-order native item completion and new stream IDs. Disconnection reduces control capabilities as before. A current pending approval is never resolved by a history gap, cursor reset, or local “seen” action. Deferred data cannot cross a source or stream boundary. When recovery is unavailable, keep the loss visible rather than repeatedly offering an action that cannot recover it.

**Acceptance tests:**

- Real fake-provider supervisor bursts of 300 and 3,000 events report exact missing ranges 2–45 and 2–2,745 from the current fixture; roster 2 and pending 1 remain. The UI distinguishes specific stream loss from generic partial source coverage.
- The integrated 5-row SQLite case with 3,000 provider events retains both results, its relationship and its delegation record. It may report a provider event gap, but must not label those available results or the team as lost. The two buried-record cases report a stream gap and bounded source coverage; missing-result counts are not inferred by subtracting provider event counts. These units remain separate in both API fields and copy.
- An actor-missing result is deferred, then emitted once when that exact actor appears. Mismatched source/native identity, repeated replay, duplicate recipients and self links do not merge identities or fabricate relationships.
- Participant never appears: queue stays bounded; eviction produces a loss marker. Stream reset and process restart cases do not accept stale requests or resend a turn.
- WorkBrief and notebook exercise 32×14, 80×24 and 120×32 with long labels; warning text remains inspectable without hiding the current approval controls.
- Run existing stale-approval, uncertain-send, no-auto-resume and native-ID tests unchanged. Add an explicit assertion that reconciling observations produces zero provider mutations.

**Measurement:** compare replay event counts and semantic result/edge sets against the independent fixture log. Record queue size and bounded batch work. Do not interpret the compositor timing budget as an ingestion or provider guarantee.

## D2 — Keep local retention fair and explain what was evicted

**Priority:** medium-high. **Problem:** a global FIFO of 512 collaboration records allows one noisy project to expel the only unread delivery in another. This happens even while B remains present and its text survives in ordinary worker history.

**Chosen behavior:** retain a bounded live notebook, not a durable transcript archive. Preserve the existing 512 total collaboration-record budget initially. On each distinct insert that exceeds 512, evict one record from the project with the largest retained count. Tied projects are ordered by the timestamp of their oldest retained record, then canonical OfficeId. Within that chosen project, evict the minimum `(timestamp, actor ID, native event ID)` tuple. Repeat only if still over budget. An upsert first replaces the prior `(actor, native event ID)` record and updates its partition membership; it does not temporarily count both versions. This makes one-project floods consume their own history first. It does not promise to retain every unread result indefinitely. When all projects compete or a project's own history exceeds its share, record the local loss explicitly.

**Interfaces and ownership:**

1. World owns retention independently of UI reading markers. Use the event's known project boundary and native actor identity for attribution; do not assign an unknown participant to a convenient project merely to make a row visible. Preserve `(actor, native event ID)` upsert rules, time ordering of the public iterator, and source identity separation.
2. Add `World::history_window(&OfficeId)` returning structured local-retention facts: retained count, oldest retained timestamp, evicted count, `last_eviction_ordinal` and `last_evicted_record_at`. The ordinal is the local ingestion order; the timestamp is explicitly the evicted record's source timestamp, not wall-clock time when eviction happened. These values describe observations retained by this process, not full provider coverage. A retained oldest timestamp must not imply a continuous interval without holes.
3. Bound retention metadata too: at most 512 project-window entries, with least-recently-observed eviction for entries that no longer have retained records. Define recency by a monotonic ingestion ordinal updated on each accepted distinct collaboration insert or materially changed upsert; rejected older versions and duplicate replay do not update it. Choose the smallest ordinal, then lexicographically smallest `OfficeId`. Use a saturating ordinal with the same deterministic ID tie-break at saturation; never read wall-clock time implicitly in World. If that still requires discarding a window, set a process-level `older_project_windows_unknown` flag; a returning project without an entry receives unknown prior history, never a false zero-loss window. Keep the flag monotonic during the process lifetime and test overflow beyond 512 projects. Source history before process start remains unknown independently of these local counters.
4. Deliveries and Changes use this metadata for empty states: `No deliveries remain in this local window; 1 record was evicted` rather than wording that implies no delivery was ever recorded. WorkBrief distinguishes surviving plain text from retained evidence marked `Result`. Offer the existing original-conversation inspection route when available; do not invent a new provider capability.
5. Keep `ReviewMemory` keys unchanged. Local review markers can outlive their evidence; they must not resurrect content or authorize source actions. Do not make core depend on UI markers to decide what is safe to delete.

**Migration:** no transcript persistence is added. Runtime loss counters start as unknown for previous process history; existing saved visit/review markers continue to load. Source-level partial coverage and local eviction are separate facts in serialization and UI. Existing 512-limit tests change from global oldest eviction to bounded/fair eviction; total count remains bounded.

**Failure handling:** deduplicated/upserted records do not count as additional retained records. Late events, unknown projects, project removal and provider source aliases must not corrupt counts. An empty or restarted World cannot state that it has complete history since a persisted visit. If a later collector replays a lost record, accept it using existing identity rules but do not erase a gap unless its completeness can actually be established.

**Acceptance tests:**

- One unreviewed result in B plus 513 messages in A leaves B's delivery inspectable, total retained records≤512, and A reports its eviction.
- Exact one-quiet-project allocation: B retains 1 and A retains 511; A's first 2 of 513 records are evicted, B's record is not. Repeating an existing native event changes no count and creates no extra eviction.
- Exact 20-project allocation: insert 50 distinct equal-weight records per project, with monotonically increasing timestamps and stable IDs. Final total 512; eight projects retain 25 and twelve retain 26, so maximum allocation differs from minimum by 1. Replaying the identical ordered log yields exactly the same retained IDs. This expectation applies after all 20 have supplied sufficient records, not during initial partial arrival.
- Exact tie-break fixture: three projects A/B/C each have 171 records, inserted in that order with unique ascending timestamps; after the 513th insert, A has 170, B and C 171, and A's oldest record is the one evicted. A second fixture with identical oldest timestamps selects canonical OfficeId first; equal-time records inside that partition select `(actor ID, native event ID)` lexically. A late insertion uses its recorded timestamp, not arrival order.
- A project's own excessive history triggers a visible local-eviction warning. No promise of permanent unread retention is made.
- Insert one record for each project `p000` through `p512`, with strictly increasing timestamps and arrival ordinals. Both record and metadata budgets remain 512; `p000` is removed and `older_project_windows_unknown` becomes true. Reinsert `p000` with a later timestamp: `p001` is retired, `p000` has one retained record and unknown prior history, both budgets stay 512, and no prior eviction count is fabricated as zero. Duplicate replay cannot change metadata recency.
- Restart with persisted visit markers, removal/reappearance, duplicate replay, equal timestamps and incomplete actor metadata produce truthful coverage.
- At 32/80/120 columns the empty-state distinction is readable and the full explanation is available. Existing Deliveries result-evidence tests and provider-approval separation remain unchanged.

**Measurement:** replay the same independent event log before/after, report retained results by project, eviction counts, total records and peak allocation. Recheck the 20-project/50-thread workload. Any later proposal to increase 512 or add disk persistence needs a separate storage/retention and resource measurement.
