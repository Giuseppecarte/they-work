# Moderator protocol — 45 minutes

Use the participant's normal terminal and comfortable font/size. Start at
120×36 only if that is comfortable; log the actual size and capability. The app
opens on synthetic data, never their personal conversation store. Do not teach
the shortcuts or metaphors before the first tasks. The moderator knows the
application; that advantage must not leak into the initial observation.

| Minutes | Activity | Capture |
| --- | --- | --- |
| 0–4 | Explain the fictitious project scenario, consent to notes/optional recording, ask normal multi-project routine. | Existing tools, number of concurrent projects, normal terminal, access needs they volunteer. |
| 4–9 | First-exposure orientation and ten-second glance task in assigned first condition. | Exact answer, confidence, wrong inferences, visible scope. |
| 9–17 | Workflow block A, triage or project return according to order. | Actions, backtracks, assistance, predicted effects versus observed effects. |
| 17–25 | Workflow block B, the other workflow. | Same measures; flag prior learning. |
| 25–35 | Compare remaining two conditions on identical facts; include keyboard-only roundtrip. | Completion, errors, recognition, focus recovery, movement interpretation, preference with reason. |
| 35–41 | Open exploration: their real recurring workflow, missing information and willingness to replace an existing step. | Concrete recent example; current workaround; frequency and cost. |
| 41–45 | Debrief, explain synthetic-provider boundaries, hand out optional three-workday diary. | Top friction, most useful feature, next use case; no feature voting without a task. |

At ten seconds, ask for an answer and let the participant continue; it is an
orientation checkpoint, not a forced failure. For workflow tasks stop at four
minutes of no progress and record “not completed within task time.” Offer one
neutral hint only after recording the unaided outcome. Never silently count
completion after a hint as unaided success.

Allowed neutral prompts: “What do you expect this to do?”, “What are you looking
for?”, “What makes you think that?”, “Where would you go next?” Avoid “Try
Attention”, “That is only a seen marker”, or pointing at the intended control.
Ask participants to predict a consequential action before clicking, but do not
ask them to perform any real approval. If using the local fake-provider task,
the moderator explains beforehand that no command is executed and the decision
goes only to a fixture process.

## Record at each task

- Start state, presentation condition, source freshness, terminal/cell geometry.
- Task start/end time, completion and correctness; meaningful navigation actions,
  backtracks, unprompted help use, moderator assistance.
- Exact answer to who/what/where/next action and confidence from 1 to 5.
- Whether project, conversation, source, visible page and total scope stayed clear.
- Any confusion caused by color, characters, posture, motion or abbreviations.
- Verbatim remarks only when actually said; distinguish quote from moderator note.

Do not rank task time without correctness. Fast approval of the wrong request is
a failure. “Could see the button” is different from knowing its consequence.
Record keyboard focus order and recovery after closing overlays separately from
pointer success. Do not claim screen-reader accessibility unless someone has
actually used that assistive technology with the application.

## Analysis after each session and after all five

Spend ten minutes after each session coding observations while memory is fresh.
Keep the original note and add interpretation in a separate field. After all
five, cluster by user goal, not by screen. Compare first exposure with learned
performance, both provider backgrounds, and graphics availability. Keep missing
sessions and unavailable conditions explicit. A feature with zero exposure has
no usability verdict.

Review the three-day diary before prioritizing a new persistent inbox, more
animation, or new navigation. The moderated session can expose comprehension
problems; it cannot establish whether a tool earns a daily place in someone's
multi-project routine.
